# Smart Sender — вебхуки

Тестове завдання Senior Frontend Engineer: вхід, список вебхуків із пагінацією та пошуком, редагування.
API імітує MSW за контрактом із завдання.

**Демо:** https://denton341.github.io/smart-sender-webhooks/
Сайт на GitHub Pages. Бекенд — це MSW-мок у браузері, тож для перегляду нічого запускати не треба.
Деплой — `npm run deploy` ([`scripts/deploy-pages.sh`](scripts/deploy-pages.sh)): скрипт проганяє lint і тести, збирає застосунок під шлях `/smart-sender-webhooks/` і публікує `dist/` у гілку `gh-pages`.

## Запуск

Потрібен Node.js 20 або новіший.

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # 4 автотести (Vitest + msw/node)
npm run typecheck  # tsc -b
npm run lint
npm run build
```

**Тестовий акаунт:** `demo@smartsender.dev` / `password123`

Сесія живе 30 секунд. Запитів за таймером немає: клієнт дізнається, що сесія закінчилась, з першого 401 і тоді викликає rotate.
Щоб це побачити, відкрийте DevTools → Network (вкладка записує лише поки відкрита), почекайте пів хвилини й зробіть будь-яку дію: буде `401 → /auth/token/rotate → повтор 200`.
MSW також пише кожен запит у консоль.

Червоні рядки `Failed to load resource: … 401 / 400 / 422` у консолі очікувані. Chrome так позначає кожну відповідь із не-2xx статусом, а тут ці статуси є частиною сценарію: сесія закінчилась, перевірка сесії при старті, невірний пароль.

## Стек

React 19, TypeScript у strict mode (плюс `noUncheckedIndexedAccess`), Vite, React Router 7, TanStack Query 5, react-hook-form, zod, MSW 2, Vitest.
UI-бібліотеки немає: модалка на нативному `<dialog>` і невеликий CSS-файл.

Версії зафіксовано на останніх, що працюють на будь-якому Node 20: Vite 8 вимагає Node 20.19+, а MSW 3, React Router 8 і Vitest 5 — Node 22+.

## Структура

```
src/
  api/                транспорт (CSRF, 419, 401 → rotate), ендпоінти, zod-схеми, ApiError
  auth/               fingerprint, стан сесії, signIn / signOut / startSession, LoginPage, RequireAuth
  features/webhooks/  запити (TanStack Query), параметри в URL, список, пошук, пагінація, модалка редагування
  shared/             UI-примітиви, Dialog, перенесення серверних помилок у форму
  mocks/              MSW-бекенд за контрактом; ті самі обробники працюють у браузері й у тестах
  app/                роутинг, layout, провайдери, екземпляри api і queryClient
```

Залежності йдуть в один бік: `api` нічого не знає про React і стан, `auth` і `features` використовують `api`, UI використовує їх.

## Ключові рішення

### Сесія та повтори запитів

Уся мережева логіка зосереджена в одному файлі — [`src/api/http.ts`](src/api/http.ts). Компоненти й запити TanStack Query не знають про CSRF чи 401: для них запит або вдається, або завершується `ApiError`.

- **401 → rotate → один повтор.** Захищений запит отримує 401, клієнт викликає `/auth/token/rotate` і повторює запит рівно один раз.
- **Один спільний rotate.** Кожен запит запам'ятовує «покоління» сесії, у якому його відправлено. Усі 401 одного покоління чекають на той самий rotate. Це стосується і 401, що прийшов уже після завершення rotate: такий запит бере готовий результат замість запуску нового rotate.
- **Rotate не запускає rotate.** Усі `/auth/*` запити йдуть з `auth: false`, тож механізм повтору на них не поширюється.
- **Кінець сесії.** Помилка rotate або повторний 401 після успішного rotate викликають подію `onSessionExpired`. У відповідь застосунок очищує кеш і стан, а `RequireAuth` відправляє на `/login` і запам'ятовує адресу, з якої прийшов користувач. Після входу він повертається туди ж, разом зі сторінкою й пошуком.
- **`device_session_token`** існує лише як локальна змінна всередині `signIn`: його одразу обмінюють на сесію через `/auth/token/issue` і ніде не зберігають.
- **`fingerprint`** — 32 hex-символи з `crypto.getRandomValues`. Генерується один раз і зберігається в `localStorage`. Якщо сховище заблоковане, значення живе в пам'яті вкладки.
- **Токени сесії бачить лише мок** (аналог HttpOnly-cookie). Клієнт знає тільки статус і профіль користувача: невелике сховище на `useSyncExternalStore`.
- **Старт застосунку.** Клієнт запитує `/v1/me`. Із реальним бекендом cookie пережила б перезавантаження, і користувач лишився б у системі. Мок тримає стан у пам'яті, тому після F5 у мережі видно `401 → rotate 400 → екран входу`. Завдання це допускає, і параметри списку з URL після входу застосовуються.
- **Вихід.** Клієнт викликає `/auth/token/revoke` (best-effort), потім `queryClient.clear()` і переходить у стан «анонімний».

### CSRF

- Перед першим запитом виконується `GET /csrf`. Токен кешується, а паралельні запити чекають на один і той самий виклик.
- Токен додається до POST і PUT.
- На 419 клієнт скидає токен і запитує новий, після чого повторює запит один раз. Якщо паралельний запит уже встиг оновити токен, повторного скидання немає.
- Усі запити мають заголовок `X-Requested-With: XMLHttpRequest`.

### Список

- URL — єдине джерело правди для `page` і `search` (`useWebhookListParams`).
- Кожна зміна додає запис в історію, тому працюють «назад» і «вперед». Значення за замовчуванням в URL не пишуться.
- Пошук застосовується з затримкою 300 мс і скидає сторінку на першу.
- Поле пошуку синхронізується з URL при навігації історією. Символи, набрані поки оновлюється URL, не губляться.
- `keepPreviousData`: під час переходу між сторінками попередня сторінка лишається на екрані, притемнена, доки не прийдуть нові дані.
- Стани:
  - завантаження;
  - помилка з кнопкою повтору;
  - порожній результат у трьох варіантах: вебхуків немає; нічого не знайдено (з кнопкою «очистити пошук»); сторінки не існує.

### Редагування

- Модалка — це вкладений маршрут `/webhooks/:id` поверх списку. Параметри списку лишаються в URL, тому модалка переживає перезавантаження і закривається на ту саму сторінку списку.
- Валідує сервер. Поля з 422 `payload` потрапляють у відповідні поля форми через `setError`. Невідомі поля та інші помилки показуються як загальна помилка форми ([`src/shared/form-errors.ts`](src/shared/form-errors.ts)).
- Клієнтську валідацію свідомо не дублював, щоб серверні помилки було видно. Її легко додати через zod-resolver.
- Після збереження оновлюється кеш деталей, і вебхук одразу змінюється в закешованих сторінках списку. Потім ці сторінки інвалідуються, бо перейменований вебхук може більше не відповідати пошуку.

### Типізація

- Відповіді API валідуються zod-схемами на межі, а типи (`Webhook`, `WebhookList`, `Me`) виводяться зі схем.
- `http.request` має перевантаження: зі схемою повертає `Promise<T>`, без схеми — `Promise<void>`.
- Стан сесії описано як discriminated union: `restoring | anonymous | authenticated`.

### Мок

- `createHandlers(baseUrl)` — фабрика, кожен виклик дає чистий стан. Браузер і тести використовують ті самі обробники.
- Перевірки йдуть у порядку middleware: `X-Requested-With` (400) → CSRF на POST/PUT (419) → сесія (401) → бізнес-логіка.
- 27 вебхуків, стабільний порядок.
- Капча: будь-який непорожній `X-Captcha-Token`.
- Сервіс-воркер реєструється через обгортку [`public/msw-worker.js`](public/msw-worker.js). Вона не пускає до MSW запити з `cache: 'only-if-cached'`, які робить DevTools при відкритті. Інакше MSW передає їх у `fetch()`, а той для сторінок, відкритих навігацією всередині застосунку, падає з `Failed to fetch`. Згенерований `mockServiceWorker.js` лишається без змін.

## Тести

[`src/api/http.test.ts`](src/api/http.test.ts) працює з `msw/node` і справжніми обробниками мока. Підробляється лише `Date`, тож спрацьовує справжній 30-секундний TTL сесії.

1. **Обов'язковий:** два паралельні запити отримують 401 → один rotate → обидва повтори успішні.
2. Rotate повертає помилку → обидва запити завершуються 401, `onSessionExpired` викликається один раз.
3. Після успішного rotate повтор знову отримує 401 → сесія завершується, другого rotate немає.
4. 419 → новий `GET /csrf` → один повтор.

Кожен тест перевірено на навмисно зламаних версіях транспорту: без спільного rotate, без повтору на 419, без завершення сесії після rotate, що не вдався, і після повторного 401. Тест для відповідного випадку падає.

## Що не зроблено / можна покращити

- Компонентних і e2e-тестів у репозиторії немає: за завданням покрито логіку сесії.
- Немає підтвердження при закритті модалки з незбереженими змінами.
- Пагінація лише «Попередня / Наступна» без номерів сторінок: даних на три сторінки.
- Немає i18n: інтерфейс англійською, повідомлення сервера — як у контракті.
- Rotate виконується лише у відповідь на 401, як вимагає контракт. Проактивне оновлення до закінчення 30 секунд не робив.
